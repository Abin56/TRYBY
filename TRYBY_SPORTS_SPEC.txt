================================================================================
  PHASE A — PRODUCT STRATEGY REVIEW
================================================================================

─── INFORMATION ARCHITECTURE PROBLEMS ─────────────────────────────────────────

PROBLEM 1: Flat navigation with no sports context
  Current: Trending | New Arrivals | Best Sellers | Categories | Deals
  Risk:    Generic links that feel like any dropship site
  Fix:     Sport-first mega menu (Cricket > Football > Gym > Running > Recovery)

PROBLEM 2: No category hierarchy
  Current: Categories are extracted dynamically from mock data
           ("Desk & Productivity", "Home & Living" — wrong domain entirely)
  Risk:    Zero relevance to sports buyer intent
  Fix:     Hardcoded sports taxonomy with subcategory drill-down

PROBLEM 3: Search has no sports intelligence
  Current: Cmd+K palette filters product names only
  Risk:    "football jersey size XL" will return nothing useful
  Fix:     Search with sport tags, size filters, team name support

PROBLEM 4: No size/variant system
  Current: Products have no size, color, or variant concept at all
  Risk:    Sports products (jerseys, shoes, gear) all require variants
  Fix:     Variant model in product type (size, color, stock per variant)

PROBLEM 5: Checkout has no guest path awareness
  Current: Navbar shows "Sign In" but no auth exists — clicking breaks
  Risk:    100% of users will see broken auth flow
  Fix:     Guest checkout + post-purchase account creation prompt

PROBLEM 6: PDP has no sports-specific trust signals
  Current: Generic "Fast Delivery", "Easy Returns", "Secure Payment"
  Risk:    Sports buyers need: Size Guide, Authenticity, Official License
  Fix:     Sport-specific trust: Certified Gear, Size Chart, Team Authenticity

─── CUSTOMER JOURNEY GAPS ──────────────────────────────────────────────────────

MISSING: Discovery → Intent signal capture
  A gym user and a cricket player land on same homepage with same hero.
  No sport-selector, no personalization, no "shop by sport" entry point.

MISSING: Social proof at decision point
  Reviews exist as a homepage section. Zero reviews on the PDP review form.
  Buy decision happens on PDP — reviews must appear there.

MISSING: Urgency mechanics
  No stock counters. No "X people viewing this". No limited-edition signals.
  Sports gear sells on scarcity + hype. None implemented.

MISSING: Post-purchase lifecycle
  Order Success page exists but is a dead end.
  No: "Complete your kit", "Track order", "Refer a friend", loyalty points.

MISSING: Mobile-first sports experience
  Sports buyers primarily shop on phones. Cart drawer width is 420px fixed.
  No bottom-sheet cart on mobile, no swipe gestures on PDP gallery.

─── CONVERSION FUNNEL RISKS ────────────────────────────────────────────────────

  Homepage → PLP:      No sport-entry CTA, just generic "Shop Now"
  PLP → PDP:           No quick-view, no size on card hover, no wishlist on hover
  PDP → Cart:          Add to Cart exists but no upsell ("Complete your kit")
  Cart → Checkout:     No coupon field in cart drawer
  Checkout → Payment:  3 shipping options hardcoded (not weight/pincode based)
  Payment → Success:   No order tracking link, no WhatsApp notification hook

─── SUPPLIER INTEGRATION READINESS ─────────────────────────────────────────────

  Current:  ZERO. All data is static mock.ts.
  Risk:     No product sync, no inventory, no pricing rules, no supplier margin
  Required: Supplier model, product sourcing table, cost price tracking, MOQ

─── SCALABILITY RISKS ──────────────────────────────────────────────────────────

  1. Zustand cart is localStorage only — no server cart, no cross-device sync
  2. No ISR — every product page is client-rendered with mock data
  3. Admin and Store are two completely separate Next.js apps sharing nothing
     (no shared types, no shared UI, no API layer)
  4. No CDN image pipeline — Unsplash direct URLs will be slow in production
  5. No error boundaries on any page

─── ROUTE HANDLER PATTERNS ─────────────────────────────────────────────────────

Every route handler follows this pattern:

  import { NextRequest, NextResponse } from "next/server"
  import { auth } from "@/lib/auth"
  import { db } from "@/lib/db"
  import { z } from "zod"

  export async function GET(req: NextRequest) {
    try {
      const session = await auth()
      // if route requires auth: if (!session) return unauthorized()

      const { searchParams } = req.nextUrl
      // parse + validate params with zod

      const data = await db.model.findMany({ ... })
      return NextResponse.json({ data }, { status: 200 })
    } catch (err) {
      return NextResponse.json(
        { error: "Internal server error" },
        { status: 500 }
      )
    }
  }

─── ERROR HANDLING ──────────────────────────────────────────────────────────────

  lib/api.ts — shared response helpers:

  success(data, status = 200)      → { data, timestamp }
  error(message, status, code)     → { error: { message, code }, timestamp }
  unauthorized()                   → error("Unauthorized", 401, "UNAUTHORIZED")
  forbidden()                      → error("Forbidden", 403, "FORBIDDEN")
  notFound(entity)                 → error(`${entity} not found`, 404, "NOT_FOUND")
  validationError(issues)          → error("Validation failed", 422, "VALIDATION_ERROR")

─── SECURITY STRATEGY ───────────────────────────────────────────────────────────

  1. Auth.js session on every protected route
  2. Role check (ADMIN / MANAGER) on all /api/admin/* routes
  3. Input validation via Zod on every POST/PATCH
  4. SQL injection: Prisma parameterized queries (automatic)
  5. CORS: restricted to own domains only
  6. Webhook verification: Razorpay HMAC signature check
  7. Cloudinary: signed uploads only (no unsigned upload key exposed)
  8. Rate limiting: Upstash Redis + @upstash/ratelimit
     — Auth endpoints: 10 req / minute per IP
     — API endpoints: 100 req / minute per user

─── RATE LIMITING ───────────────────────────────────────────────────────────────

  middleware.ts handles rate limiting before route handlers:

  import { Ratelimit } from "@upstash/ratelimit"
  import { Redis } from "@upstash/redis"

  const ratelimit = new Ratelimit({
    redis: Redis.fromEnv(),
    limiter: Ratelimit.slidingWindow(100, "1 m"),
  })

─── LOGGING STRATEGY ────────────────────────────────────────────────────────────

  Use: pino (structured JSON logging)

    info  — successful operations (order created, payment confirmed)
    warn  — suspicious activity (multiple failed auth, coupon abuse)
    error — exceptions, DB errors, payment failures

  All logs include: timestamp, userId, orderId, route, duration

      Credentials({ ... })
