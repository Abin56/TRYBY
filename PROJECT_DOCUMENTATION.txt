1. PROJECT OVERVIEW
=================================================

WHAT IS TRYBY?
--------------
TRYBY is a premium B2C sports merchandise dropshipping e-commerce platform
built for the Indian market. It sells official and premium sports jerseys,
equipment, and accessories — initially focused on cricket, football, gym &
fitness, and running categories.

TRYBY is not a traditional inventory-holding retailer. It operates as a
dropshipping marketplace where:
- Suppliers hold the physical inventory
- TRYBY markets and sells to customers
- Suppliers fulfill and ship orders
- TRYBY earns commission on each sale
- Suppliers receive payouts after a settlement hold period

BUSINESS MODEL
--------------
Revenue Sources:
  1. Commission: TRYBY charges suppliers a percentage-based commission
     per delivered order (configurable by category, supplier, or globally)
  2. GST on Commission: TRYBY charges 18% GST on its commission amount
  3. Shipping Deduction: Shipping cost may be partially deducted from
     supplier earnings depending on commission rule configuration

Key Financial Flow:
  Customer pays ₹X → TRYBY receives ₹X via Razorpay
  → Supplier earns ₹X minus commission minus GST minus shipping
  → After 7-day hold period, supplier can withdraw to bank

Pricing Strategy:
  - Suppliers provide cost price
  - TRYBY calculates selling price via margin % + minimum profit guarantee
  - Automatic price sync when supplier cost changes

DROPSHIPPING WORKFLOW (HIGH LEVEL)
-----------------------------------
  1. Customer browses TRYBY store, adds to cart
  2. Customer places order with online payment (Razorpay) or COD
  3. Order flows to supplier dashboard
  4. Supplier accepts, packs, and ships via courier integration
  5. Shiprocket/Delhivery generates AWB and tracking
  6. Webhook events update order tracking in real time
  7. On delivery, settlement is created with 7-day hold
  8. After hold expires, supplier balance is credited
  9. Supplier requests payout to their registered bank account

SUPPLIER WORKFLOW
-----------------
  1. Apply via supplier portal (form + document upload)
  2. Admin reviews and approves supplier application
  3. Supplier signs agreement (versioned, digital)
  4. Supplier uploads products or enables sync profile
  5. Admin maps supplier SKUs to TRYBY product variants
  6. Inventory syncs automatically at configured frequency
  7. Supplier receives orders via dashboard
  8. Supplier updates order status (packed → shipped)
  9. Supplier tracks SLA performance score
  10. Supplier monitors wallet, ledger, settlements
  11. Supplier requests payout when balance is available

CUSTOMER WORKFLOW
-----------------
  1. Customer visits TRYBY store (or mobile app)
  2. Browses homepage, categories, search
  3. Views product detail, selects size/variant
  4. Adds to cart or wishlist
  5. Applies coupon code (optional)
  6. Enters shipping address
  7. Selects payment method (online / COD)
  8. Pays via Razorpay checkout
  9. Receives order confirmation email + in-app notification
  10. Tracks shipment via tracking page
  11. Receives delivery notification
  12. Can raise return request within return window
  13. Earns loyalty points on delivered orders
  14. Can write product review after delivery

ADMIN WORKFLOW
--------------
  1. Monitor dashboard: revenue, orders, pending actions
  2. Review new supplier applications
  3. Approve/reject products from suppliers
  4. Manage product catalog, pricing, categories
  5. Process and resolve customer returns
  6. Moderate product reviews
  7. Manage coupon campaigns and promotions
  8. Monitor inventory levels and sync health
  9. Manage shipping and courier integrations
  10. Approve supplier payouts
  11. Review fraud alerts and blacklist management
  12. View financial reports: profit, commissions, GST
  13. Run marketing campaigns (email, WhatsApp)
  14. Manage content: homepage blocks, announcements, SEO

SUPER ADMIN WORKFLOW
--------------------
  1. Full access to all admin functions
  2. Manage admin team: add/remove admins, set roles
  3. Set fine-grained permissions per admin
  4. Force-logout any admin session
  5. Access complete audit trail of all admin actions
  6. Toggle system feature flags
  7. Configure maintenance mode
  8. Monitor system health: background jobs, services
  9. Manage security: blacklists, COD rules, fraud thresholds
  10. View all supplier agreements and override commission rules

2. SYSTEM ARCHITECTURE
=================================================

MONOREPO STRUCTURE
------------------
  Dropshipping/
  ├── store/          ← Main app (Next.js): storefront + admin + supplier portal
  ├── admin/          ← Standalone admin dashboard (separate Next.js app, currently UI-only)
  └── [docs]/         ← Architecture docs, specs, status files

NOTE: The `store/` directory is the primary production application. The
`admin/` directory is a separate standalone dashboard that appears to be
a UI prototype/reference — it uses mock data and does not share the
Prisma database. All production admin functionality lives in store/app/admin/.

FRONTEND ARCHITECTURE
---------------------
Framework: Next.js 16.2.6 (App Router, React Server Components)
Language: TypeScript 5
Styling: Tailwind CSS 4
Animations: Framer Motion 12
Icons: Lucide React
Toast Notifications: Sonner
State Management: Zustand 5
Form Handling: React Hook Form + Zod validation
UI Primitives: Radix UI (accessible, unstyled components)
Table Library: TanStack React Table (admin data tables)
Charts: Recharts (admin analytics)

Rendering Strategy:
  - Server Components by default (data fetching at server)
  - Client Components for interactive UI (cart, checkout, modals)
  - Edge Middleware for route protection and auth checks
  - ISR/SSR for product pages, SSG for static pages

BACKEND ARCHITECTURE
--------------------
Runtime: Node.js (Next.js API Routes)
ORM: Prisma 5.22.0
Database: PostgreSQL (hosted on Neon)
Authentication: NextAuth.js v5 (beta) with JWT strategy
API Style: REST (Next.js App Router Route Handlers)
Error Tracking: Sentry (client + server + edge)

Key architectural patterns:
  - Route Handlers in app/api/* for all API endpoints
  - Prisma transactions for multi-step operations
  - Integer arithmetic (paise) for all financial calculations
  - Idempotency keys for webhooks and settlements
  - Double-entry ledger for supplier financial records
  - Fire-and-forget pattern for non-critical side effects

DATABASE ARCHITECTURE
---------------------
Database: PostgreSQL (Neon - serverless)
Schema: Prisma schema at store/prisma/schema.prisma (2997 lines)
Migrations: Located at store/prisma/migrations/
Models: 75+ Prisma models covering all business domains

Key design decisions:
  - All financial amounts stored in PAISE (integer), not rupees (decimal)
  - Immutable audit logs (AuditLog, SupplierLedger, StockSyncLog)
  - Soft deletes via `isArchived` flags on products
  - Event-sourced order status via OrderStatusHistory
  - Idempotency via unique constraint on WebhookEvent(eventId, eventType)
  - Running balance snapshot on each SupplierLedger entry

API ARCHITECTURE
----------------
All APIs follow Next.js App Router conventions:
  - Files: app/api/[path]/route.ts
  - Methods: export async function GET/POST/PATCH/PUT/DELETE
  - Auth: Checked via auth() from lib/auth.ts
  - Role checks: via hasPermission() from lib/rbac.ts
  - Validation: Zod schemas before DB operations
  - Error format: { error: string } with appropriate HTTP status codes
  - Rate limiting: lib/rate-limit.ts (sliding window per IP:route)

Total API count: ~195+ route handlers

Versioning:
  - v1 endpoints under /api/v1/ (mobile app compatibility)
  - Default endpoints unversioned (web app)

EXTERNAL SERVICES ARCHITECTURE
-------------------------------
  Payment:   Razorpay → /api/webhooks/razorpay
  Shipping:  Shiprocket → /api/webhooks/shiprocket
             Delhivery → /api/webhooks/delhivery
  Email:     Resend (transactional emails)
  Images:    Cloudinary (CDN, transformations)
  OAuth:     Google (via NextAuth.js)
  Errors:    Sentry (frontend + backend + edge)

AUTHENTICATION FLOW
-------------------
Customer Authentication:
  1. Customer visits /auth/signin
  2. Options: Email/Password or Google OAuth
  3. NextAuth.js handles OAuth flow and JWT creation
  4. JWT stored in httpOnly cookie (auth_token)
  5. Session validated on each protected request via middleware.ts

Admin Authentication:
  1. Admin visits /admin (redirected to /admin/login if not authenticated)
  2. Email + password login (no OAuth for admins)
  3. Password verified against AdminProfile.passwordHash (bcrypt, 12 rounds)
  4. JWT issued with role and permissions claims
  5. Middleware checks role for every /admin/* and /api/admin/* request
  6. SUPER_ADMIN gated routes checked additionally
  7. AdminSession created per login (force-logout capable)

Supplier Authentication:
  1. Supplier visits /supplier/login
  2. Email + password login
  3. Supplier account linked to User record with UserRole.SUPPLIER
  4. Session carries supplier context

Role Hierarchy:
  SUPER_ADMIN > ADMIN > [role-specific managers] > SUPPORT_AGENT

JWT Contents:
  - user.id, user.email, user.role
  - adminProfile.role (for admins)
  - adminProfile.permissions (extra permissions beyond role defaults)

Purpose: Supplier application and approval flow

APIs: /api/supplier/apply
Models: Supplier, SupplierDocument, User

  1. Supplier fills application form (company name, GST, bank details, products)
  2. Uploads documents (GST certificate, PAN, bank statement)

9. BUSINESS WORKFLOWS
=================================================

--- ORDER PLACEMENT FLOW ---

Step 1: Customer browses and adds to cart
  → CartItem created with userId + variantId + quantity
  → CartItem quantity stored in DB (persists across sessions)

Step 2: Customer proceeds to checkout (/checkout)
  → POST /api/checkout called with: addressId, couponCode, paymentMethod
  → Server validates:
    a. Cart is not empty
    b. All variant stocks are available (variant.stock >= quantity)
    c. Pincode is serviceable (not in restricted list)
    d. Coupon is valid: active, in date range, not exceeded usage limit,
       per-user limit not reached, minimum order amount met
    e. Fraud checks: customer risk level, COD restrictions, blacklist

Step 3: Order created in DB (within Prisma transaction)
  → Order record created (status: PENDING)
  → OrderItem records created for each cart item
  → ProductVariant.stock decremented (reserved stock incremented)
  → Product.soldCount / soldToday / soldThisWeek incremented
  → Coupon.usageCount incremented
  → CartItem records deleted
  → OrderFulfillmentAllocation created (warehouse reservation)
  → SupplierSLA record created (timer starts)

Step 4: Payment processing
  → ONLINE: Razorpay order created, payment modal shown to customer
    → Customer completes payment via card/UPI/netbanking
    → Razorpay sends webhook: payment.captured
    → Webhook handler: Payment.status → CAPTURED, Order.status → CONFIRMED
    → OrderStatusHistory entry created
    → Customer notified (email + in-app)
  → COD: Order immediately set to CONFIRMED (no payment webhook)
    → COD eligibility checked (risk level, order amount limits)

Step 5: Order flows to supplier
  → Order appears in supplier dashboard (status: CONFIRMED)
  → Supplier receives notification (in-app + email)
  → SLA timer: Supplier must accept within 4 hours

Step 6: Supplier processes order
  → Supplier accepts order (SLA: acceptedAt recorded)
  → Supplier packs order (status: PROCESSING)
  → SLA timer: Must ship within 48 hours of creation
  → Supplier marks as shipped: enters AWB code or triggers Shiprocket

Step 7: Shipping
  → If Shiprocket auto AWB enabled: Shiprocket creates shipment automatically
  → AWB code assigned, tracking URL generated
  → Shipment record created in DB
  → Courier picks up parcel
  → Shiprocket webhooks arrive as order moves through transit:
    PICKED_UP → IN_TRANSIT → OUT_FOR_DELIVERY → DELIVERED

Step 8: Delivery
  → DELIVERED webhook received from Shiprocket
  → Shipment.status → DELIVERED, deliveredAt = timestamp
  → Order.status → DELIVERED
  → ShipmentEvent created with final delivery details
  → Customer notification: "Your order has been delivered!"
  → Loyalty points credited to customer (EARN_ORDER)

Step 9: Settlement creation
  → On DELIVERED status:
    a. Commission calculated (CommissionRule lookup: SUPPLIER → CATEGORY → GLOBAL)
    b. GST on commission calculated (18%)
    c. Net supplier earning = order amount - commission - GST - shipping deduct
    d. SupplierSettlement created with status=HOLDING, holdUntil = now + 7 days
    e. SupplierLedger entry created: ORDER_EARNING (credit)
    f. SupplierLedger entry created: COMMISSION_DEDUCTION (debit)
    g. SupplierLedger entry created: GST_DEDUCTION (debit)
    h. Supplier.pendingBalance updated

Step 10: Settlement release (after 7-day hold)
  → Cron job: releaseMaturedSettlements() runs periodically
  → Settlements with holdUntil <= now and status=HOLDING updated to AVAILABLE
  → Supplier.pendingBalance decremented, Supplier.availableBalance incremented
  → Supplier notification: "₹X is now available for withdrawal"

--- RETURN FLOW ---

Step 1: Customer requests return
  → Customer in /account/orders/[id] clicks "Return Items"
  → POST /api/returns (or checkout API)
  → ReturnRequest created (status: PENDING)
  → Customer selects items, quantities, and reason
  → Customer uploads photos (via Cloudinary)

Step 2: Admin reviews return
  → Admin sees return in /admin/returns
  → Checks return reason, photos, order eligibility
  → Admin approves or rejects

Step 3a: Return approved
  → ReturnRequest.status → APPROVED
  → Return pickup scheduled (via courier)
  → Customer notified: return pickup scheduled

Step 4: Item received and verified
  → Admin marks item received and condition verified
  → ReturnRequest.status → COMPLETED

Step 5: Refund issued
  → POST /api/admin/payments/[id]/refund
  → Razorpay refund API called with order's payment ID
  → Payment.refundedAmount updated
  → If full refund: Order.status → REFUNDED
  → If partial: Order.status stays, refundedAmount tracked
  → Customer notified: "Refund of ₹X has been initiated"

Step 6: Supplier deduction
  → applyReturnDeduction() called with orderId
  → SupplierLedger entry created: REFUND_DEDUCTION (debit)
  → Supplier.pendingBalance or availableBalance decremented
  → SupplierSettlement for this order updated (amount reduced)

Step 3b: Return rejected
  → ReturnRequest.status → REJECTED
  → Customer notified with rejection reason

--- SUPPLIER SETTLEMENT FLOW ---

Step 1: Order delivered
  → createOrderSettlement() called (idempotent)
  → SupplierSettlement created: status=HOLDING, holdUntil = deliveredAt + holdDays

Step 2: Ledger entries created
  → ORDER_EARNING: grossAmount = orderAmount in paise
  → COMMISSION_DEDUCTION: commissionAmt in paise
  → GST_DEDUCTION: gstOnCommission in paise
  → net = grossAmount - commissionAmt - gstOnCommission - shippingDeduct
  → Each entry has runningBalance snapshot

Step 3: Holding period
  → Default: 7 days from delivery
  → SettlementDispute can extend hold if raised

Step 4: Hold release
  → releaseMaturedSettlements() finds HOLDING settlements past holdUntil
  → Updates: status=AVAILABLE
  → Updates Supplier.availableBalance (Prisma transaction)
  → HOLDING_CREDIT ledger entry created

Step 5: Supplier requests payout
  → Supplier clicks "Request Payout" in portal
  → Payout record created: status=PENDING, amount in paise
  → Admin sees in /admin/payouts queue

Step 6: Admin approves payout
  → Admin reviews and clicks Approve
  → Payout.status → APPROVED

Step 7: Admin processes payout
  → Transfers funds via bank (manual process)
  → Admin enters UTR number
  → Payout.status → PROCESSED
  → recordPayoutDebit() called:
    → PAYOUT_DEBIT ledger entry created
    → Supplier.availableBalance decremented
    → Supplier.processingBalance adjusted

--- INVENTORY SYNC FLOW ---

Step 1: Sync profile configured
  → SupplierSyncProfile: supplierId, frequency, marginPct, bufferStockPct
  → SupplierSkuMap: supplierSku → variantId mapping set up by admin

Step 2: Sync triggered (scheduled or manual)
  → syncSingleSupplier(supplierId) called
  → New syncSessionId generated (UUID)

Step 3: Stock sync (syncSupplierInventory)
  → For each SupplierSkuMap entry for this supplier:
    a. Look up supplier's reported stock quantity
    b. Apply buffer: finalQty = supplierQty × (1 - bufferStockPct/100)
    c. If isIgnored: skip (log: SKIPPED)
    d. If NO mapping found: log (NO_MAPPING)
    e. Update ProductVariant.stock = finalQty
    f. If stock = 0 and autoHideOnZero: set Product.isHidden = true
    g. If stock > 0 and product was hidden: set Product.isHidden = false
    h. Create StockSyncLog entry (status: SUCCESS/FAILED)

Step 4: Price sync (syncSupplierPrices)
  → For each SupplierSkuMap with new costPrice:
    a. If isPriceOverride: skip
    b. Calculate new selling price:
       sellingPrice = max(costPrice × (1 + marginPct/100), costPrice + minProfitAmt)
    c. Update ProductVariant.price
    d. Create PriceSyncLog (oldCostPrice, newCostPrice, oldSellingPrice, newSellingPrice)

Step 5: Session summary
  → syncSingleSupplier returns: total, success, failed, noMapping counts
  → StockSyncLog entries queryable by syncSessionId

--- SHIPPING FLOW ---

Step 1: Order confirmed
  → Order.status = CONFIRMED
  → If shiprocket_auto_awb feature flag enabled:
    → Shiprocket API called automatically

Step 2: Shiprocket shipment creation
  → createShipment(order, supplier) called
  → Payload sent to Shiprocket: order details, pickup location, items, weight
  → Shiprocket returns: shipment_id, awb_code, assigned_courier, label_url
  → Shipment record created in DB: awbCode, courier, shipmentId, labelUrl
  → Order.status → PROCESSING (if auto)

Step 3: Label generation
  → Admin accesses /admin/shipping/labels
  → generateLabel(shipmentId) or generateBulkLabel([ids])
  → PDF label returned for printing

Step 4: Pickup
  → schedulePickup() called for warehouse pincode
  → Courier collects from warehouse/supplier

Step 5: In-transit webhook events
  → Shiprocket sends webhook: POST /api/webhooks/shiprocket
  → Webhook verified (HMAC-SHA256 signature)
  → AWB code matched to Shipment record
  → Status mapped: Shiprocket status → ShipmentStatus enum
  → ShipmentEvent created (location, timestamp, description)
  → Order.status updated (PROCESSING → SHIPPED → DELIVERED etc.)
  → Customer notified at OUT_FOR_DELIVERY and DELIVERED milestones

Step 6: Delivery confirmed
  → DELIVERED webhook → Order.status = DELIVERED
  → Shipment.deliveredAt = timestamp
  → Settlement created (7-day hold starts)
  → Loyalty points credited to customer
  → Customer email sent: "Your order has been delivered"

Step 7: RTO (Return to Origin)
  → If undeliverable, Shiprocket sends RTO status events
  → Order.status → RETURNED
  → Shipment.rtoInitiatedAt, rtoDeliveredAt tracked
  → Admin notified for manual resolution
  → Settlement may be voided or adjusted

11. FEATURE FLAGS
=================================================

Feature flags are database-backed toggles stored in the FeatureFlag model.
Checked via lib/feature-flags.ts which caches values for 60 seconds.
Managed via /admin/system/feature-flags (SUPER_ADMIN only).
On first boot, seedDefaultFlags() creates all flags with default values.

FLAG KEY                     | DEFAULT | PURPOSE
-----------------------------|---------|------------------------------------------
loyalty_enabled              | false   | Enable loyalty points earning and redemption
referral_enabled             | false   | Enable customer referral program
supplier_marketplace_enabled | false   | Show public supplier profiles at /suppliers
reviews_enabled              | true    | Allow customers to submit product reviews
community_enabled            | false   | Enable /community social feed page
google_oauth_enabled         | true    | Show Google Sign-In button on auth pages
whatsapp_notifications       | false   | Send WhatsApp messages via configured provider
cod_enabled                  | true    | Allow Cash on Delivery payment option
coupons_enabled              | true    | Allow coupon code entry at checkout
wishlist_enabled             | true    | Allow add-to-wishlist on products
maintenance_bypass_admins    | true    | Admins can access site during maintenance
prelaunch_mode               | false   | Show splash page (/splash) instead of homepage
shiprocket_auto_awb          | false   | Auto-generate AWB via Shiprocket on order confirm

Implementation Notes:
  - Flags are checked with isEnabled(key) which returns false on DB error (fail-safe)
  - Cache TTL: 60 seconds (invalidated immediately when flag is toggled)
  - If flag doesn't exist in DB, seedDefaultFlags() creates it with default value
  - Front-end checks flags server-side in Server Components
  - Dependencies: whatsapp_notifications requires WhatsApp provider credentials
  - Dependencies: shiprocket_auto_awb requires valid Shiprocket credentials

12. CRON JOBS & BACKGROUND JOBS
=================================================

Background job infrastructure uses the SystemJob model for tracking.
Job types tracked: PENDING, RUNNING, COMPLETED, FAILED, CANCELLED
Max retry attempts: 3 (configurable per job)

NOTE: The platform has the INFRASTRUCTURE for scheduled jobs (SystemJob model,
lib functions) but the actual scheduler/cron runner is not yet implemented
via a cron service. Currently jobs may be triggered manually or via API.
A production deployment would need a cron service (Vercel Cron, pg_cron,
or external scheduler) to call the trigger APIs on schedule.

PLANNED/REQUIRED SCHEDULED JOBS:
----------------------------------

JOB: Supplier Inventory Sync
  Trigger: Per-supplier schedule (15m / 30m / 1h / 6h / 24h)
  Function: syncAllSuppliers() or syncSingleSupplier(supplierId)
  File: lib/supplier-sync.ts
  Effect: Updates ProductVariant.stock, hides/shows products, logs to StockSyncLog

JOB: Supplier Price Sync
  Trigger: Tied to inventory sync schedule
  Function: syncSupplierPrices() within syncSingleSupplier()
  File: lib/supplier-sync.ts
  Effect: Recalculates selling prices based on margin, logs to PriceSyncLog

JOB: Release Matured Settlements
  Trigger: Daily (recommend 12:00 AM IST)
  Function: releaseMaturedSettlements()
  File: lib/finance.ts
  Effect: Moves settlements from HOLDING → AVAILABLE when holdUntil has passed
  Impact: Updates Supplier.pendingBalance and Supplier.availableBalance

JOB: SLA Breach Monitoring
  Trigger: Every 30 minutes
  Function: refreshOpenSLAs()
  File: lib/sla.ts
  Effect: Flips SLA status ON_TIME → AT_RISK → BREACHED as time passes
  Impact: Alerts sent when BREACHED, supplier score recomputed

JOB: Customer Segmentation Update
  Trigger: Daily
  Function: Recompute CustomerSegment tags for all users
  Effect: Updates NEW_CUSTOMER, LOYAL, VIP, AT_RISK, CHURNED, etc.
  Impact: Used for targeted marketing campaigns

JOB: Abandoned Cart Recovery
  Trigger: Every 1 hour
  Function: Find carts abandoned for 1+ hour, send recovery emails
  File: lib/notifications.ts, AbandonedCart model
  Effect: Sends email/WhatsApp with cart contents and incentive

JOB: Loyalty Points Expiration
  Trigger: Daily
  Function: Find LoyaltyPoints with expiresAt <= today, create EXPIRE entries
  Effect: Reduces effective loyalty balance

JOB: Fraud Risk Score Refresh
  Trigger: Daily
  Function: recomputeCustomerRisk() for all customers with recent order activity
  File: lib/fraud.ts
  Effect: Updates CustomerRiskProfile.riskScore and riskLevel

JOB: Supplier Scorecard Recompute
  Trigger: Daily
  Function: Recompute all supplier performance/fulfillment/quality/trust scores
  Effect: Updates Supplier composite scores, SLA scores

API TRIGGER ENDPOINTS:
  POST /api/admin/supplier-sync/run    → Manual sync trigger
  GET  /api/admin/jobs                 → View job status
  POST /api/admin/jobs                 → Create/trigger background job

   Admin:      http://localhost:3000/admin

14. TROUBLESHOOTING GUIDE
=================================================

COMMON ISSUES & FIXES
---------------------

ISSUE: Admin login fails / "Invalid credentials"
FIX:
  1. Check AdminProfile exists for this email:
     npx prisma studio → AdminProfile table
  2. Verify password hash is set (not null)
  3. Re-run setup script: npx tsx scripts/setup-super-admin.ts
  4. Check if account is disabled: AdminProfile.isDisabled = false
  5. Check login attempt lockout: LoginAttempt records

ISSUE: Google OAuth not working
FIX:
  1. Verify GOOGLE_CLIENT_ID and GOOGLE_CLIENT_SECRET are correct
  2. Check google_oauth_enabled feature flag is ON
  3. Verify redirect URI in Google Console: {APP_URL}/api/auth/callback/google
  4. Check AUTH_URL matches the actual deployment URL

ISSUE: Payments not processing / Razorpay errors
FIX:
  1. Verify RAZORPAY_KEY_ID and RAZORPAY_KEY_SECRET are correct
  2. Check if using test vs live credentials (test: rzp_test_*, live: rzp_live_*)
  3. Verify NEXT_PUBLIC_RAZORPAY_KEY_ID matches RAZORPAY_KEY_ID
  4. Check Razorpay dashboard for failed payment logs
  5. Webhook not arriving: verify webhook URL in Razorpay dashboard
  6. Webhook signature mismatch: verify RAZORPAY_WEBHOOK_SECRET

ISSUE: Orders stuck in PENDING (payment captured but order not confirmed)
FIX:
  1. Check WebhookEvent table: did payment.captured arrive?
  2. Check Razorpay webhook logs for delivery failures
  3. Manually update order status in /admin/orders if needed
  4. Verify webhook endpoint: {APP_URL}/api/webhooks/razorpay is accessible

ISSUE: Shiprocket AWB not generating
FIX:
  1. Check shiprocket_auto_awb feature flag is enabled
  2. Verify SHIPROCKET_EMAIL and SHIPROCKET_PASSWORD are correct
  3. Check if Shiprocket token is expired (re-login happens automatically)
  4. Check order address is complete (pincode, address, city, state)
  5. Check STORE_PINCODE is set to a valid pickup pincode
  6. Test serviceability: /api/shipping/serviceability?pincode=XXXXX

ISSUE: Product images not uploading
FIX:
  1. Verify Cloudinary credentials (CLOUDINARY_API_KEY, CLOUDINARY_API_SECRET)
  2. Check CLOUDINARY_CLOUD_NAME matches the Cloudinary account
  3. Check upload API: POST /api/admin/upload
  4. Verify Cloudinary account is not at storage limit
  5. Check browser console for CORS errors

ISSUE: Emails not sending
FIX:
  1. Verify RESEND_API_KEY is valid
  2. Check RESEND_FROM_EMAIL domain is verified in Resend dashboard
  3. Check spam folder for test emails
  4. Review Resend dashboard logs for bounces/failures
  5. Test by sending a manual notification from admin panel

ISSUE: Database connection errors
FIX:
  1. Verify DATABASE_URL is correct and database is running
  2. For Neon: check if connection pooling mode is correct
  3. Try: npx tsx scripts/verify-db.ts
  4. Check Neon dashboard for connection limit issues
  5. For local PG: ensure PostgreSQL service is running

ISSUE: Supplier stock sync not working
FIX:
  1. Check SupplierSyncProfile.isEnabled = true
  2. Verify SupplierSkuMap entries exist for this supplier
  3. Check StockSyncLog for last sync session and errors
  4. Manually trigger: POST /api/admin/supplier-sync/run {supplierId}
  5. Verify sync is being triggered (check SystemJob table)

ISSUE: Settlements not releasing
FIX:
  1. Check SupplierSettlement where status=HOLDING and holdUntil <= now
  2. Manually trigger: releaseMaturedSettlements() via admin job API
  3. Verify no DISPUTED settlements blocking release
  4. Check cron job is actually running (SystemJob table)

ISSUE: Feature flag changes not taking effect immediately
FIX:
  - Flags are cached for 60 seconds
  - Call invalidateCache(key) or wait 60 seconds
  - In development, restart dev server if cache doesn't clear

ISSUE: Rate limit errors (429 Too Many Requests)
FIX:
  - Rate limits are per IP:route, sliding window
  - Check RateLimitEntry table for IP and route
  - Webhook rate limits: 200/min (Razorpay), standard for others
  - Development: disable rate limiting or use different IPs

DEBUGGING TOOLS
---------------
Prisma Studio (DB browser):
  npm run db:studio → http://localhost:5555

API Testing:
  Use browser DevTools → Network tab for admin/supplier portal APIs
  Or Postman/Insomnia with session cookie from logged-in browser

  All runtime errors automatically captured
  Access at: sentry.io (your project)

  Also in: /admin/payments/audit

LOG LOCATIONS

  - Console output in terminal running `npm run dev`
  - Browser DevTools → Console for client-side errors
  - Sentry captures all unhandled errors automatically

Production (Vercel):
  - Vercel Dashboard → Functions tab → per-request logs
